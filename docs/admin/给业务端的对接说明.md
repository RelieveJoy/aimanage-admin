## 一、先说清楚现状

管理员端已完成 **AD1–AD6** 六个故事，并且共享后端已经就位：

| 已完成 | 位置 |
|---|---|
| 三角色鉴权（拦截器 + `@RequireRole`） | `backend/.../security/` |
| **审计账本切面**（方案 A2） | `backend/.../audit/` |
| 用户 / 部门 / 项目 / 成员 全套接口 | `backend/.../admin/` |
| 审计账本检索界面 | 管理端「审计账本」页 |

**重要：后端是同一份 `backend/`，三个端共用。** 你们不用另起后端，直接在这个仓库里加自己的 Controller / Service 就行。

### 两条不要碰的红线

1. **不要改 `com.aimanage.audit` 包** —— 审计切面是所有端共用的基础设施。
2. **`/api/admin/**` 路径不要碰** —— 这个前缀被拦截器硬编码保护，非 ADMIN 一律 403。

## 二、需要你们配合的三件事

### 需求 1️⃣　审计注解：让业务变更进账本　【重要】

**为什么需要**：审计账本（方案特色一）现在只记录了管理员的操作。**你们那边的任务状态变更、需求修改、排期调整，一条都没进账本** —— 因为切面只拦挂了注解的方法。

方案 DoD 第 4 条要求「**审计账本 100% 覆盖写操作**」，缺了你们这块就不成立。而且方案里有一句时序上的话：

> "审计启动越早，事件流越长 —— 这是本项目最重要的时序决策。"

越晚接，可演示的历史数据越少。

**怎么做**：在每个写方法上加一行注解 + 每个变更字段加一行 `AuditContext.change`。

```java
@Auditable(type = AuditLog.TARGET_TASK, action = AuditLog.ACTION_UPDATE, projectIdArg = 0)
@Transactional
public void updateStatus(Long taskId, String newStatus) {
    Task old = taskMapper.selectById(taskId);

    // ← 这一行是你唯一要手写的：只有你知道"哪个字段从什么变成了什么"
    AuditContext.change("状态", old.getStatus(), newStatus);

    old.setStatus(newStatus);
    taskMapper.updateById(old);
}
```

**操作人、角色快照、时间、落库、异常隔离全部由切面处理**，你一行都不用写。

参数说明：

| 注解属性 | 含义 |
|---|---|
| `type` | 对象类型，`AuditLog.TARGET_*` 常量。你们的任务/需求需要**自己加常量**（见下） |
| `action` | `ACTION_CREATE` / `ACTION_UPDATE` / `ACTION_DELETE` |
| `projectIdArg` | 第几个参数是项目 ID（`-1` 表示没有）。**填上这个，"按项目检索"才能筛到** |
| `targetIdArg` | 第几个参数是目标对象 ID（新增场景用 `AuditContext.targetId(id)` 代替） |

**你们需要在 `AuditLog` 里加两个常量**（现在只有 PROJECT / PROJECT_MEMBER / USER / DEPARTMENT）：

```java
public static final String TARGET_TASK = "TASK";
public static final String TARGET_REQUIREMENT = "REQUIREMENT";
```

> 新增场景记得补 `AuditContext.targetId(新对象的id)` —— 因为 ID 是插入后才生成的，
> 参数列表里拿不到。

**注意**：审计写入**绝不阻塞业务**。切面吞掉所有异常只记日志，写账本失败不会让你的业务方法报错，放心加。

### 需求 2️⃣　只读数据接口：让管理员能看进度　【AD7】

**为什么需要**：方案 AD7「只读观测」—— 管理员要盯进度但不插手。现在管理端的「只读观测」菜单是灰的，就卡在这。

**需要你们做两件事**：

**(a) 提供两个只读数据接口**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/projects/{id}/kanban` | 看板数据 |
| GET | `/api/projects/{id}/gantt` | 甘特数据 |

返回什么结构你们定，我按你们的来渲染。

**(b) 保证后端对 ADMIN 的读写行为**

- ADMIN 调用上面两个 GET → **放行**
- ADMIN 调用任何业务写接口（POST/PATCH/DELETE）→ **必须 403**

第 (b) 条不是可选项：管理员一旦能改任务，三角色权限模型就废了，审计账本里会出现"管理员改了成员的任务"，责任判定那套叙事直接自杀。这也是方案 DoD 第 2 条要测的。

> **不需要你们做"只读组件"** —— 管理端是独立前端工程，跨工程复用组件太折腾。
> **你们只要给数据接口，我自己画只读视图。** 这样对我们两边都最省事。

---

### 需求 3️⃣　申请加人入口：让审批流动起来　【AD8】

**为什么需要**：管理端的「审批与通知」也是灰的，卡在提交侧。

**背景约定**：PM **不能**自己往项目里加人，必须走申请 → 管理员批准。这样"组织架构 + 项目成员"完全归管理员，和需求方要的"明确每个项目的 PM 和成员是谁"对得上。

**接口**：`POST /api/requests`

```json
{ "projectId": 1, "targetUserId": 5, "reason": "测试人力不足，需要补充人手" }
```

**表已经建好了**，你们直接写入即可（`db/schema.sql` 里的 `join_request`）：

| 字段 | 说明 |
|---|---|
| `project_id` | 项目 |
| `applicant_id` | 发起人（从 UserContext 取当前登录用户） |
| `target_user_id` | 被申请加入的人 |
| `reason` | 申请理由 |
| `status` | 写入时固定 `PENDING` |

批准 / 拒绝由**管理端**处理（管理端会写 `reviewer_id` / `review_comment` / `reviewed_at`，并在通过时自动写 `project_member` 和一条审计）。**你们只需要负责提交那一侧。**

> 如果这个接口你们希望我来写（就是一个 insert），说一声，10 行的事，你们只要在前端加个按钮调它。

## 三、优先级建议

| 优先级 | 需求 | 理由 |
|---|---|---|
| 🔴 **高** | 需求 1（审计注解） | **越晚接，可演示的历史数据越少**。而且它不改你们的业务逻辑，加注解就行 |
| 🟡 中 | 需求 3（申请加人） | 管理端审批界面我做完了就能接上 |
| 🟢 低 | 需求 2（只读接口） | 等你们的看板/甘特做出来再说，不急 |
